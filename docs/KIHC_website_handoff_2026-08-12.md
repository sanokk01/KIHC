## 1. 사이트 콘셉트 및 현재 방향

KIHC 웹사이트는 한국인재역량연구회의 연구 방향과 공신력을 소개하고, 연구자료·소식·홍보자료를 제공하며, 연구 제휴·자문·강연 문의로 연결하는 비영리 연구기관형 사이트입니다.

현재 화면 방향은 다음과 같습니다.

- 기관 신뢰도를 우선하는 네이비·골드 기반의 절제된 연구기관 디자인
- 연구자료를 메인 핵심 콘텐츠로 노출하는 구조
- 모바일에서도 메뉴, 검색, 목록, 상세 콘텐츠를 무리 없이 읽을 수 있는 반응형 구조
- 관리자 1명이 Supabase DB의 콘텐츠를 등록·수정하는 단일 운영자 방식
- 문의 전환을 위해 연구·자문·강연 범위를 명확히 보여주는 문의 페이지

## 3. 현재까지 완료한 작업

### 3.1 전체 모바일 최적화

- 900px, 720px, 480px, 360px 구간을 기준으로 레이아웃을 재정리했습니다.
- 긴 제목, 이메일, 전화번호, 메타데이터가 화면 밖으로 넘치지 않도록 줄바꿈 규칙을 추가했습니다.
- 버튼과 링크의 모바일 터치 영역을 약 40~44px 이상 확보했습니다.
- 페이지별로 달랐던 컨테이너 여백, 제목 크기, 섹션 간격을 모바일 기준으로 보정했습니다.
- 가로 스크롤이 필요한 탭과 메뉴는 페이지 전체가 밀리지 않고 해당 영역만 스크롤되도록 수정했습니다.

### 3.2 모바일 햄버거 메뉴

발견 문제:

- 햄버거 메뉴는 열리지만 상단 메뉴의 하위 메뉴가 모바일에서 열리지 않거나 데스크톱 hover 규칙과 충돌했습니다.
- 메뉴가 열린 동안 뒤쪽 페이지가 함께 스크롤될 수 있었습니다.
- 화면 회전 또는 데스크톱 폭으로 전환할 때 열린 메뉴 상태가 남을 수 있었습니다.

수정 내용:

- 모바일 전용 하위 메뉴 토글을 추가했습니다.
- 열림/닫힘 상태와 접근성 속성(`aria-expanded`, `aria-controls`)을 연결했습니다.
- 메뉴가 열리면 본문 스크롤을 잠그고, 닫히면 원래 상태로 복원합니다.
- ESC 키, 메뉴 링크 선택, 데스크톱 폭 전환 시 메뉴가 닫히도록 처리했습니다.
- 햄버거 아이콘이 닫기 아이콘으로 전환되는 애니메이션을 정리했습니다.

### 3.3 메인 페이지

- 주요 연구자료 슬라이더의 인라인 고정 폭을 제거하고 반응형 CSS로 통합했습니다.
- 모바일에서는 카드가 한 화면에 읽기 좋은 폭으로 표시되며 옆 콘텐츠를 스와이프할 수 있습니다.
- 연구자료의 `image_url`이 있으면 대표 이미지를 사용하고, 없으면 KIHC 텍스트 커버를 표시합니다.
- 팝업이 열리면 뒤 페이지 스크롤이 잠기며 모바일 화면 높이를 넘을 경우 팝업 내부만 스크롤됩니다.

### 3.4 연구자료 목록 및 상세 페이지

- 고급 검색의 라디오, 기간, 분류, 검색어 입력을 작은 화면에서 세로 배치했습니다.
- 연구자료 썸네일, 제목, 저자·날짜 메타데이터가 모바일에서 겹치지 않도록 재배치했습니다.
- 상세 페이지의 표지, 기본정보, 목차, 요약, 키워드 영역을 모바일 1열로 변경했습니다.
- 긴 논문 제목과 키워드가 화면 밖으로 넘치지 않도록 수정했습니다.
- 기능이 연결되지 않았던 본문 글자 크기 버튼은 제거했습니다.
- 연구자료 대표 이미지는 목록, 상세, 메인의 주요 게시물에서 같은 `image_url`을 사용합니다.

### 3.5 소식 목록 및 공지 상세 페이지

- 데스크톱 표 형태의 목록을 모바일에서 번호·제목·날짜 중심의 카드형 행으로 전환했습니다.
- 모바일에서 중요도가 낮은 조회수·첨부 아이콘 열을 숨겨 제목 가독성을 확보했습니다.
- 카테고리, 제목, 작성일, 개최일, 첨부파일, 이전·다음 글 영역의 모바일 배치를 정리했습니다.
- 긴 공지 제목과 본문 문장이 화면 밖으로 넘치지 않도록 수정했습니다.

### 3.6 소개 페이지

### 3.9 관리자 로그인 및 보안

기존 문제:

- localhost 여부만으로 관리자 권한을 허용하는 임시 인증 방식이 있었습니다.
- DB 접속 문자열이 코드 기본값에 포함되어 있었습니다.
- 실제 관리자 계정·세션 테이블과 로그인 검증이 없었습니다.

수정 내용:

- localhost 자동 관리자 우회를 제거했습니다.
- 지정된 관리자 아이디 1개만 사용할 수 있도록 DB 제약조건과 애플리케이션 검증을 적용했습니다.
- 웹에서 관리자 계정을 추가 생성하는 가입 기능은 제공하지 않습니다.
- 비밀번호 원문 대신 랜덤 salt가 포함된 scrypt 단방향 해시만 DB에 저장합니다.
- 로그인 성공 시 12시간 유효한 HttpOnly 세션 쿠키를 발급하고, 세션 토큰은 해시로 DB에 저장합니다.
- 관리자 API는 로그인 세션이 유효한 경우에만 콘텐츠를 읽고 수정합니다.
- DB 접속 문자열 하드코딩을 제거하고 Netlify 환경변수만 사용합니다.
- Supabase Transaction Pooler에 맞춰 prepared statement를 끄고 연결 풀 기본값을 1로 제한했습니다.

관리자 계정 원문 비밀번호는 이 인수인계 문서에 기록하지 않습니다. 대화 또는 다른 경로에 노출된 기존 비밀번호는 운영 전에 별도의 강력한 값으로 교체해야 합니다.

## 4. 아직 남아 있는 제한 및 추가 개발 항목

### 4.1 Supabase Storage 파일 업로드 - 추가 개발

현재 DB에는 이미지 주소를 저장하는 `content_records.image_url`과 파일 메타데이터용 `media_assets`가 있습니다. 관리자 화면에서 공개 이미지 URL을 붙여 넣으면 연구자료 목록·상세·메인에 표시됩니다.

그러나 관리자 화면에서 파일을 선택해 Supabase Storage로 직접 업로드하는 API는 아직 연결되지 않았습니다. 현재 업로드 API는 503 응답을 반환하며 파일 선택 입력도 비활성화되어 있습니다.

필요한 후속 작업:

1. Supabase Storage에 공개 이미지 버킷 생성
2. 허용 MIME 유형과 최대 용량 결정
3. Netlify 서버 전용 Storage 인증 환경변수 등록
4. 관리자 업로드·교체·삭제 API 구현
5. 미사용 이미지 정리 정책 결정

### 4.2 문의 폼 전송 방식 - 기획 결정

현재 방식은 `mailto:` 링크로 사용자의 메일 앱을 여는 방식입니다. 웹사이트 DB에는 개인정보가 저장되지 않는 장점이 있지만, 메일 앱이 설정되지 않은 사용자는 전송하지 못할 수 있고 문의 이력도 사이트에서 관리할 수 없습니다.

기획팀은 다음 중 하나를 결정해야 합니다.

- 현재 방식 유지: 개인정보 저장 없음, 구현 단순
- Netlify Forms 사용: 사이트에서 제출, 스팸 방지·알림 설정 필요
- 별도 메일 API 사용: 자동 접수 메일·운영 알림 가능, 서비스 계정 필요
- Supabase 문의 테이블 사용: 관리자 이력 관리 가능, 개인정보 보유·파기 정책 필요

### 4.3 법정 고지 페이지 - 콘텐츠 필요

현재 푸터의 개인정보처리방침, 이용약관, 이메일무단수집거부 링크는 전용 문서 페이지가 아니라 문의 페이지로 연결됩니다. 공개 운영 전 다음 문서를 받아 전용 페이지를 만들어야 합니다.

- 개인정보처리방침
- 홈페이지 이용약관
- 이메일무단수집거부 안내
- 문의 폼에서 사용할 개인정보 수집·이용 동의문

### 4.4 등록번호 표시 방식 - 확인 필요

현재는 비영리 등록번호 일부를 마스킹하고 ‘등록번호 필요 시 문의’ 버튼을 제공합니다. 이 방식이 단체의 법적·행정적 표시 의무와 내부 정책에 맞는지는 기획팀 또는 관련 전문가가 확인해야 합니다. 필요하면 전체 번호 표시 또는 마스킹 범위를 조정해야 합니다.

### 4.5 관리자 운영 정책 - 확인 필요

- 관리자 계정은 1개만 허용됩니다.
- 별도의 웹 비밀번호 변경, 비밀번호 찾기, MFA 기능은 없습니다.
- 비밀번호 교체 시 새로운 scrypt 해시를 만들어 DB의 기본 관리자 행을 갱신해야 합니다.
- 계정 공유가 필요한 경우 접근자와 교체 주기, 퇴사·담당 변경 시 절차를 정해야 합니다.
- 로그인 반복 시도에 대한 별도 영구 차단·속도 제한은 아직 없습니다.

- 공지 상세의 본문, 첨부, 이전·다음 글이 자연스러운지
- 메인 주요 게시물 카드 스와이프와 화살표 버튼이 자연스러운지
- 팝업이 작은 화면에서 닫기 버튼까지 표시되는지
- 문의 폼 입력과 개인정보 동의, 이메일 앱 전환이 작동하는지
- 푸터 정보와 등록번호 문의 버튼의 문구가 적절한지

### 5.2 콘텐츠·정책 결정

- 공식 기관명 한글·영문 표기 확정
- 주소를 푸터에 표시할지 결정하고 공식 주소 제공
- 비영리 등록번호 전체 공개 여부와 마스킹 범위 확정
- 개인정보처리방침 등 법정 고지문 제공
- 문의 접수 방식을 mailto, Netlify Forms, 메일 API, DB 저장 중 선택
- 문의 예상 회신 시간 문구 제공 여부 결정
- 관리자 계정 1개 운영 정책 승인
- 한국어·영어 콘텐츠의 공식 번역 검수
- 연구자료 상세에서 PDF 다운로드를 제공할지 결정
- 홍보자료 상세를 공개할지 문의 유도형으로 유지할지 결정

## 7. Supabase에서 운영자가 해야 할 작업

### 7.1 작업 전 준비

1. Supabase 프로젝트 관리자 권한이 있는 계정으로 접속합니다.
2. 운영 데이터가 이미 있다면 `content_records`, `site_singletons`, `media_assets`를 먼저 내보내 백업합니다.
3. 기존 DB 비밀번호가 대화·문서·화면 캡처에 노출되었으므로 새 DB 비밀번호로 재설정합니다.
4. DB 비밀번호와 관리자 로그인 비밀번호는 서로 다른 값으로 사용합니다.
5. 새 비밀번호는 소스 코드, 기획 문서, 메신저에 기록하지 않고 승인된 비밀번호 관리 도구에 저장합니다.

### 7.2 DB 초기화·보완 SQL 실행

사용 파일: `supabase/kihc_full_setup.sql`

1. Supabase Dashboard에서 해당 KIHC 프로젝트를 선택합니다.
2. 왼쪽 메뉴에서 SQL Editor를 엽니다.
3. New query를 선택합니다.
4. `supabase/kihc_full_setup.sql` 파일 전체를 복사해 붙여 넣습니다.
5. Run을 한 번 실행합니다.
6. 오류 없이 완료됐는지 확인합니다.
7. 마지막 결과에서 관리자 행이 1개이고 `password_storage`가 `scrypt hash stored`인지 확인합니다.
8. 콘텐츠 section별 `record_count`, `records_with_image` 결과를 확인합니다.

이 SQL의 영향:

- 콘텐츠 테이블과 기존 콘텐츠 원문을 삭제하지 않습니다.
- 기존 시드 항목에는 누락된 기본 필드만 보완합니다.
- 다른 관리자 행을 제거하고 기본 관리자 1개만 유지합니다.
- 기존 관리자 로그인 세션은 모두 종료합니다.
- 브라우저용 anon/authenticated 역할에서 핵심 테이블 직접 접근을 차단합니다.

오류가 발생하면 같은 SQL을 반복 실행하기 전에 오류 화면 전체를 캡처해 개발 담당자에게 전달합니다.

### 7.3 Netlify용 DB 연결 문자열 확보

1. Supabase Dashboard 상단의 Connect를 선택합니다.
2. Transaction pooler URI를 선택합니다.
3. 포트가 `6543`인지 확인합니다.
4. 새 DB 비밀번호가 반영된 연결 문자열을 복사합니다.
5. 비밀번호의 특수문자는 URL 인코딩되어야 합니다.

형식 예시:

```text
postgresql://postgres.PROJECT_REF:URL_ENCODED_NEW_PASSWORD@aws-0-REGION.pooler.supabase.com:6543/postgres
```

이 문자열은 비밀값입니다. 화면 캡처, Git, 일반 문서에 포함하지 않습니다.

### 7.4 이미지 Storage를 사용할 경우

현재 배포에 필수인 단계는 아닙니다. 관리자가 파일을 직접 업로드해야 한다는 기획 결정이 난 뒤 진행합니다.

1. Storage에서 전용 버킷을 생성합니다. 예: `kihc-media`
2. 공개 웹사이트 이미지라면 공개 버킷 사용 여부를 결정합니다.
3. JPG, PNG, WEBP, GIF 중 허용 형식을 결정합니다.
4. 관리자 업로드 기준 최대 용량은 6MB 이하를 권장합니다.
5. 서버 전용 Storage 키는 브라우저 코드에 넣지 않고 Netlify 비밀 환경변수로만 등록합니다.
6. 업로드 API 구현 완료 후 생성·교체·삭제·미사용 파일 정리를 테스트합니다.

## 8. Netlify에서 운영자가 해야 할 작업

상세 입력 예시는 `netlify/environment-variables.example.txt` 파일에도 정리되어 있습니다.

### 8.1 DATABASE_URL 등록

경로: Project configuration > Environment variables > Add a variable

```text
Key: DATABASE_URL
Value: Supabase에서 새로 복사한 Transaction pooler URI
```

설정 기준:

- `Contains secret values`: 반드시 체크
- Scopes: Builds와 Functions에서 사용할 수 있어야 함. 현재 화면에서 분리 설정이 어렵다면 All scopes 사용
- Deploy contexts: Production만 운영 DB에 연결하는 것을 권장
- Deploy Preview와 Branch deploy가 운영 DB를 사용하지 않도록 주의

Value 입력란에는 `DATABASE_URL=`을 붙이지 않고 URI만 입력합니다.

### 8.2 DB_POOL_MAX 등록

```text
Key: DB_POOL_MAX
Value: 1
```

- 비밀값 체크는 필요하지 않습니다.
- DATABASE_URL과 같은 런타임 범위에 적용합니다.
- Netlify Functions의 짧은 실행 환경에서 DB 연결 수가 과도하게 늘어나는 것을 방지합니다.

### 8.3 NEXT_PUBLIC_SITE_URL 등록

```text
Key: NEXT_PUBLIC_SITE_URL
Value: https://실제-운영-도메인
```

- 실제 대표 도메인을 입력합니다.
- 기본 Netlify 도메인을 운영 주소로 사용할 경우 해당 전체 주소를 입력합니다.
- 사용자에게 공개되는 값이므로 비밀값 체크는 하지 않습니다.

### 8.4 빌드 설정 확인

프로젝트에는 다음 설정이 준비되어 있습니다.

```text
Build command: npm run build
Publish directory: .next
Node version: 22
```

Netlify의 실제 Build settings가 위 값과 일치하는지 확인합니다. package-lock.json이 있으므로 npm 설치 흐름을 사용합니다.

### 8.5 재배포

1. 환경변수를 저장합니다.
2. Deploys로 이동합니다.
3. Trigger deploy > Deploy site를 실행합니다.
4. Deploy log에서 dependency install, Next.js build, deploy 단계가 성공했는지 확인합니다.
5. 환경변수 값을 로그에 직접 출력하는 디버그 코드는 사용하지 않습니다.

### 8.6 배포 직후 필수 확인

1. 메인, 소개, 연구자료, 소식, 문의 페이지가 500 오류 없이 열리는지 확인합니다.
2. `/adminpage1/login`이 열리고 DB 연결 오류가 표시되지 않는지 확인합니다.
3. 등록된 단일 관리자 계정으로 로그인합니다.
4. 테스트용 초안 콘텐츠를 생성하고 목록에 저장되는지 확인합니다.
5. 공개 상태로 변경했을 때 공개 페이지에 표시되는지 확인합니다.
6. 연구자료에 공개 이미지 URL을 넣고 연구 목록·상세·메인에 같은 이미지가 표시되는지 확인합니다.
7. 수정·삭제 후 새로고침해 DB 내용이 유지되는지 확인합니다.
8. 로그아웃 후 관리자 API와 관리 페이지에 접근할 수 없는지 확인합니다.

배포가 실패하면 Deploy log 전체와 실패한 단계의 첫 오류 메시지를 캡처해 전달합니다. 이전 정상 배포가 있다면 Netlify의 이전 배포 재게시 기능으로 사이트 화면을 우선 복구할 수 있습니다.
